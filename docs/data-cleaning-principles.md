# 数据处理协作原则（题型与知识点共用）

> 给题型负责人、知识点负责人和工程同事的简版执行说明。
> 目标不是一次性洗完历史数据，而是稳定地产出可以逐步进入高质量数据集的样本。

## 一句话原则

```text
先发现问题 → 小批验证根因 → 人工确认规则 → 只扩大同一问题簇 → 保留证据与版本。
```

历史标签是证据，不是真值；模型结果是候选，不是自动修改指令。错标优先于漏标处理：漏标会少召回题，错标会推荐错误方向的题。

## 两类工作，使用同一套流程

| 项目 | 题型负责人 | 知识点负责人 |
|---|---|---|
| 最小处理单位 | `scope × 题型结构 × 题型名称`，必要时再细分内容模式 | `question × 末级知识点标签`，必要时按近似标签簇合并 |
| 历史标签的地位 | 只作为录入证据 | 只作为待验证标签 |
| 核心问题 | 这类题按内容应是什么题型、父题/小题如何分别打？ | 这个已有知识点是否确为解题必要点？是否错标或漏标？ |
| 首轮模型任务 | 根据题面判断题型或发现题型与内容冲突 | 判断指定末级标签是否适用 |
| 不能做的事 | 因历史题型存在就直接沿用 | 从父题继承知识点，或把 `match=true` 当真值 |
| 放大单位 | 同一录入 bug / 同一题型边界簇 | 同一标签 / 同一释义边界 / 同一共标错误簇 |

题型和知识点可以并行推进。题型 route 是知识点的 scope、分层统计和 HQ 门禁，但不应阻塞对已有末级知识点标签的直接审计。

## 统一的七步流程

### 1. 冻结输入

每次开始前记录：源文件路径与 SHA、规则本版本、代码 commit、抽样条件、模型/prompt 版本和运行目录。

源 JSONL 永远只读；输出只能写到新的 audit、silver、patch 或 HQ 目录。

### 2. 定义本批的业务边界

先写清楚本批“应该是什么”和“不应该是什么”。

题型负责人要明确：

- parent / child 是否分别处理；
- 内容特征与题型名称冲突时，以什么为准；
- 该 route 的知识点是 `required`、`optional`、`forbidden` 还是待定。

知识点负责人要明确：

- 标签的老师释义、近似标签、可共标/互斥关系；
- “解题必要”与“只是题面出现”的边界；
- 图片、音频、父题上下文缺失时是否可判。

业务边界不清时，状态应为 `unresolved`，不是自动判空或自动保留。

### 3. 小批抽样，先看真实题

先从目标单元按 parent/child、文本/图文/音频、单标签/多标签等分层抽样。盲审时默认隐藏历史标签，避免被旧数据锚定。

目标是发现**系统性模式**，不是挑几道题证明模型“看起来可以”。

### 4. 运行模型，只产出候选证据

模型输入应包含可判定的题目内容、选项、答案、解析和必要上下文；脏的题型名称/结构不要作为模型直接判断依据。

模型输出必须结构化，并保留：

```text
question_id / parent_id / is_sub_question / source_line
历史标签或目标单元
模型结论、reason、prompt_version、model、原始响应
```

模型结果的三种常见状态：

- `candidate`：有可解析结论，等待校准或人工审核；
- `uncertain`：题目信息、规则或候选范围不足；
- `error`：服务、格式或输入异常。

后两类不能静默丢弃，更不能当作负例。

### 5. 双向人工抽检并校准

不能只抽模型“通过”的题。必须分别查看正向和负向结论：

```text
模型保留 / match=true 的样本
模型删除 / match=false 的样本
```

每条人工结论只使用：

| 结论 | 含义 |
|---|---|
| `retain` | 旧标签或候选结论正确，应保留 |
| `remove` | 旧标签确实不应打，或候选结论应删除 |
| `uncertain` | 内容缺失、规则未定或需要业务裁决 |

正向抽检用于衡量“模型保留会不会带入错标”；负向抽检用于衡量“模型删除会不会误删共标或边界标签”。

### 6. 保守分流，不直接改源

所有数据至少分为四层：

| 去向 | 含义 | 是否可训练 |
|---|---|---:|
| `legacy` | 原始历史记录 | 否 |
| `audit` / `hold` | 未确认、冲突、输入不足或未校准 | 否 |
| `silver` | 规则和抽检支持的候选 | 仅辅助实验 |
| `relabel_candidate` | 明确值得替换/补标的样本 | 否，等待 patch |

只有人工确认的 `keep/drop/replace/add` patch 可以改变最终标签集合。`silver` 不是 HQ：它可能仍有漏标、题型错标或多模态缺失。

### 7. 只扩大已验证的问题簇

如果小批发现一个稳定根因，才扩大到同类数据。例如：

- 题型：阅读还原与阅读匹配的录入混淆；
- 知识点：模型把共标误当“只有一个主考点”；
- 输入：听力无文本、图片选项只有占位符；
- taxonomy：历史根节点无法映射到老师新标签树。

扩大后仍要抽检。若扩大样本的错标率、输入完整度或人工一致性变差，立即停止，不做全量推翻式清洗。

## 题型负责人的具体执行方式

题型负责人先按：

```text
scope(parent | child) × 题型结构 × 题型名称
```

建立清单，再按真实内容确定 route policy。建议每个 route 的输出状态为：

| 状态 | 含义 | 后续 |
|---|---|---|
| `approved` | 题型与父/子粒度已经业务确认 | 可作为 HQ 门禁和知识点分层条件 |
| `needs_review` | 历史名称或内容存在边界 | 继续盲审与小批验证 |
| `unmapped` | 当前无规则 | 隔离，不沿用历史标签 |
| `legacy_type_*` | 历史 taxonomy/录入问题 | 建立迁移或错标问题簇 |

题型处理的完成定义不是“给每条题都写了一个新名称”，而是：同一 route 的业务规则、样本、抽检和风险码都可复现。阅读类小题是否有知识点，必须逐类确认；不能因为“阅读”两个字统一判空。

## 知识点负责人的具体执行方式

知识点负责人按一个 active 末级标签推进：

```text
题目 × 该历史末级标签
→ 直接判别是否为解题必要点
→ true/false 双向抽检
→ 标签级校准 policy
→ silver / hold / relabel
```

一题有多个历史知识点时，必须分别验证。只有所有历史 active 知识点都有正向、身份一致的证据，才能形成题级 `silver_question_candidate`；它仍不能证明没有漏标。

对于 false、未校准或缺标题，再进入 flat shortlist 或知识点树寻找替换/补充候选。候选树和 top-k 的作用是**解决难例**，不是验证已有标签的首入口。

## 所有人共用的停止条件

出现以下情况，暂停放大并回到小批诊断：

- 人工抽检发现模型正向保留的错标；
- 模型 false 大量误删共标；
- 同一标签在某个 route、图片/音频状态下表现明显不同；
- 题目缺解析、缺图或缺听力文本，无法可靠判定；
- taxonomy 映射、释义或标签关系本身尚未确定；
- 新规则不能证明优于历史版本；
- 输出无法回溯到 source SHA、行号和规则版本。

## 每次交接只需要交付这六项

1. 本批单位：哪个 route、标签或问题簇；
2. 输入 manifest：源、规则本、commit、模型和 prompt；
3. 样本与人工抽检结论；
4. 分流统计：silver / hold / relabel，以及主要原因；
5. 新发现的根因、边界和不确定项；
6. 下一步：扩大、补规则、人工裁决，或停止。

## 最终判断标准

```text
宁可先 hold，也不要把不确定数据写成高质量真值。
宁可按标签和问题簇缓慢扩大，也不要未验证地全量重洗。
```

详细命令和数据契约见：[数据清洗执行手册](data-cleaning-playbook.md)。
